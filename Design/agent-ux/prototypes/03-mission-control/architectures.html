hub Four ways agents coordinate

One outcome, four architectures.

Every Developer Hub run is a team of agents. Depending on the task shape, the team can look very different — a single lead coordinating workers, a mesh of peers voting, a deep hierarchy, or a rigid pipeline. Below: the same three things (prompt, orchestration graph, execution log) for four distinct flows, each the most natural fit for its architecture.

hub
Supervisor · centralized 1 lead · 3 workers · aggregates results

Plan the Q2 marketing campaign launch.

A single Orchestrator owns the task. It decomposes the brief, dispatches three specialist workers in parallel, receives their artifacts, and stitches them into a final plan. Best for workflows with a well-understood decomposition and clear deliverables per specialist.

polyline
Network · decentralized 4 peers · mesh handoffs · consensus on merge

Review this pull request for production readiness.

Four specialist reviewers inspect the diff in parallel and can freely hand off findings to each other — e.g. a performance concern that surfaces a types issue. No single lead; the run completes when all peers post a verdict and consensus is reached. Great for tasks where domains overlap and there isn't an obvious top-down decomposition.

A top-level planner hands three domain leads their slice of the migration. Each lead then delegates to their own workers. Status rolls back up level by level. Chosen when the task is large, clearly domain-sliced, and each domain has its own sub-plan worth surfacing.

linear_scale
Sequential · pipeline 4 stages · strict order · each stage transforms the previous output

Turn this research paper into a customer-facing blog post.

A fixed chain: Retriever → Summarizer → Writer → Editor. Each agent consumes the previous agent's output and produces the next one. No branching, no peer chat — simple, deterministic, easy to reason about. Best when the transformation steps are well known and ordered.

extension
Mixed · composite 1 commander · 3 sub-teams · each sub-team uses its own pattern

Resolve the prod checkout outage.

Real runs rarely fit one shape. Developer Hub can compose patterns: a top-level Supervisor delegates to sub-teams, and each sub-team picks the pattern that fits its own sub-task. Here: an incident commander kicks off a sequential hotfix pipeline on the left, a peer-network investigation in the middle, and a solo comms agent on the right — all in parallel, all reporting back up.

Why mix? Different sub-tasks have different shapes. The fix needs strict ordering (diagnose → patch → deploy). The investigation benefits from peer chat (SRE and Security cross-referencing signals). Customer comms is a single, independent workstream. Forcing all three into one pattern would either over-serialize the whole run or drop the causal links that matter.

Picking a pattern

Developer Hub proposes the pattern that fits your task shape — and can combine patterns within a single run when no single shape fits. You can always regenerate or edit the team before anything runs.

hub Supervisor

Pick when: decomposition is clear & specialists don't overlap much. Watch for: single point of coordination failure.

polyline Network

Pick when: domains overlap, peer feedback improves quality. Watch for: loops / no consensus. Set a vote rule.

account_tree Hierarchical

Pick when: task is big & domain-sliced; each domain deserves its own sub-plan. Watch for: reporting latency across levels.

linear_scale Sequential

Pick when: order is known and each stage's output feeds the next. Watch for: one bad stage spoils the whole run.

extension Mixed / composite

Pick when: one shape isn't enough — parallel sub-teams need different internal patterns (e.g. incident response). Watch for: graph legibility. Label sub-teams clearly.
